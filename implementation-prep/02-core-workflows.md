# 02｜核心作業流程規格

**狀態：** Draft v0.1  
**目的：** 將入社、活動、專案與幹部交接四條流程視覺化，作為後續 wireframe、API 與資料狀態設計的共同依據。

## 1. 入社申請與審核流程

```mermaid
flowchart TD
    A[訪客瀏覽加入資訊] --> B[填寫入社申請]
    B --> C{欄位與重複申請驗證}
    C -->|失敗| D[顯示錯誤並修正]
    D --> B
    C -->|通過| E[建立申請中紀錄]
    E --> F[通知具審核權限的幹部]
    F --> G{幹部審核}
    G -->|核准| H[建立／啟用社員帳號]
    G -->|列候補| I[更新為候補並通知]
    G -->|退回／婉拒| J[更新結果與通知]
    H --> K[社員首次登入]
```

| 流程控制點 | 規格 |
| --- | --- |
| 重複檢查 | 同 Email 存在「申請中」或「候補」紀錄時，不可重複建立申請。 |
| 審核權限 | 只有被授予 `membership.review` 的幹部或網站負責人可審核。 |
| 可追溯性 | 審核結果應寫入審核者、時間、原因與歷程，不可覆蓋原紀錄。 |
| 待確認 | 核准是否需要第二人覆核、候補是否有到期日、退回與婉拒的通知文案。 |

### 1.1 已確認的招生流程覆蓋規格

```mermaid
flowchart TD
    A[訪客選擇招生梯次] --> B{校內或校外}
    B --> C[閱讀對應招生說明與時程]
    C --> D[提交申請與書審資料]
    D --> E{申請資料驗證}
    E -->|失敗| D
    E -->|通過| F[狀態：書審中]
    F --> G{書審結果}
    G -->|通過| H[通知並安排面試]
    G -->|未通過／待補件| I[通知結果或補件要求]
    H --> J[狀態：面試中]
    J --> K{面試結果}
    K -->|核准| L[建立或啟用社員資格]
    K -->|候補／婉拒| M[更新最終結果並通知]
    L --> N{校內或校外帳號啟用規則}
    N -->|校內| O[學號＋學校信箱驗證後設定密碼]
    N -->|校外| P[待確認的帳號啟用流程]
```

| 新增控制點 | 規格 |
| --- | --- |
| 招生梯次 | 校內、校外各自配置說明、開放日、書審截止、面試時段與公告日。 |
| 書審 | 審核者可登錄結果、評語、補件要求與時間；申請人只讀取對自身必要的結果。 |
| 面試 | 系統至少記錄面試安排、結果與審核歷程；視訊連結或面試細節只限審核相關人員。 |
| 帳號啟用 | 校內依已確認的學號與學校信箱認證；校外帳號流程列為阻塞性待決事項。 |

## 2. 活動建立、報名與取消流程

```mermaid
flowchart TD
    A[幹部建立活動草稿] --> B{欄位規則驗證}
    B -->|失敗| A
    B -->|通過| C[發布活動]
    C --> D{是否開放報名且未截止}
    D -->|否| E[顯示活動資訊與狀態]
    D -->|是| F[社員送出報名]
    F --> G{資格與重複報名驗證}
    G -->|失敗| H[顯示原因]
    G -->|通過| I{剩餘名額}
    I -->|有| J[建立已報名紀錄]
    I -->|無| K[建立候補紀錄]
    J --> L[通知社員與更新名單]
    K --> L
    L --> M{社員取消？}
    M -->|是且未逾期限| N[更新為已取消並釋出名額]
    N --> O[通知幹部處理候補]
```

| 流程控制點 | 規格 |
| --- | --- |
| 名額一致性 | 報名與候補判斷須在後端交易中完成，避免多人同時報名造成超收。 |
| 取消權限 | 社員只能取消自己的有效報名；幹部可依授權代為取消。 |
| 狀態顯示 | 公開頁只顯示必要的報名／候補狀態，不顯示其他社員名單。 |
| 待確認 | 活動是否允許訪客報名、是否收費、取消期限與候補遞補機制。 |

## 3. 專案建立與專案生指派流程

```mermaid
flowchart TD
    A[幹部建立專案] --> B[設定名稱、期間、可見範圍與指導幹部]
    B --> C[發布專案]
    C --> D[選擇有效社員]
    D --> E{社員資格驗證}
    E -->|不符合| F[拒絕指派並顯示原因]
    E -->|符合| G[建立 ProjectAssignment]
    G --> H[賦予專案生資料存取權]
    H --> I[通知專案生]
    I --> J{專案結束或人員異動}
    J -->|是| K[設定 Assignment 結束日]
    K --> L[回收專案限定存取權]
    L --> M[保留歷史指派與稽核紀錄]
```

| 流程控制點 | 規格 |
| --- | --- |
| 角色分離 | 專案生是 `ProjectAssignment`，幹部是 `OfficerAssignment`；同一人可以同時具備兩者。 |
| 存取範圍 | 專案資料預設只供所屬專案生與指導幹部讀取。 |
| 結案處理 | 結案後保留歷史紀錄，但專案資源是否仍允許下載必須由專案政策決定。 |
| 待確認 | 專案是否需要申請、是否可跨屆、每位專案生可加入專案上限。 |

## 4. 幹部任期與交接流程

```mermaid
flowchart TD
    A[網站負責人建立部門與職務] --> B[指派有效社員為幹部]
    B --> C[設定任期起訖與權限組]
    C --> D[任期生效]
    D --> E[幹部管理授權範圍內容]
    E --> F{交接或任期結束}
    F --> G[建立下一任職務指派]
    G --> H[移交部門資源與交接清單]
    H --> I[原職務任期結束]
    I --> J[系統回收管理權限]
    J --> K[保留內容署名與稽核紀錄]
```

| 流程控制點 | 規格 |
| --- | --- |
| 失效機制 | 任期結束後，原幹部不得再執行管理操作；不得依賴人工手動移除。 |
| 備援治理 | 網站負責人至少應有一位備援責任人，以避免單一帳號失效。 |
| 交接內容 | 部門 SOP、資源、活動草稿、待辦與權限清單需列入交接項目。 |
| 待確認 | 換屆日期、是否允許任期重疊、誰有權提前終止幹部任期。 |

### 4.1 任期到期通知覆蓋規格

```mermaid
flowchart TD
    A[每日任期排程檢查] --> B{距離 ends_on ≤ 提醒天數？}
    B -->|是且未通知| C[通知幹部、社長與網站負責人]
    B -->|否| D[維持有效職務]
    C --> E{到達 ends_on？}
    D --> E
    E -->|否| F[等待下一次排程]
    E -->|是| G[停用 OfficerAssignment]
    G --> H[撤除由該職務賦予的管理權限]
    H --> I[寫入稽核紀錄與交接待辦]
```
