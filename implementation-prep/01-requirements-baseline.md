# 01｜MVP 需求基線與使用者故事

**狀態：** 可供需求工作坊審閱的 Draft v0.1  
**範圍基準：** 訪客、社員、專案生、幹部、網站負責人；優先執行 AF-01、AF-02、AF-03、AF-06 與既有公開資訊、活動、資源、RWD 功能。

## 1. MVP 範圍凍結建議

第一期的目的不是一次取代所有社團工具，而是建立一個具備正確身份、活動、資源與專案歸屬的可信網站。下列功能列入 MVP；任務看板、QR 報到、行事曆訂閱、資源版本控管與跨屆知識地圖保留在第二期。

| 模組 | MVP 交付功能 | 對應角色 | 不納入 MVP 的功能 |
| --- | --- | --- | --- |
| 公開資訊 | 首頁、社團介紹、幹部介紹、公開公告、活動列表／詳情、加入入口。 | 訪客 | 公開留言、社群動態牆。 |
| 身分與會員 | 登入、會員申請、審核、會員狀態、個人資料與通知偏好。 | 訪客、社員、幹部、網站負責人 | 校務 SSO 與複雜多因子流程；可先採 OAuth 或 Email 登入。 |
| 活動作業 | 建立活動、報名／取消、名額、候補、名單、基本出席結果。 | 社員、幹部 | QR 報到、候補自動遞補、外部行事曆訂閱。 |
| 資源中心 | 分類、公開範圍、上傳、下載與基本更新日期。 | 社員、專案生、幹部 | 完整版本控制與到期自動下架。 |
| 專案基礎 | 建立專案、指派專案生與指導幹部、專案公告、專屬資源。 | 專案生、幹部 | 任務看板、里程碑、交付物審核與會議紀錄。 |
| 治理 | 角色權限、幹部任期、交接、稽核紀錄與網站負責人帳號治理。 | 幹部、網站負責人 | 雙人審稿、完整企業 CRM。 |

## 2. 使用者故事與驗收條件

### 2.1 訪客與入社申請

| ID | 使用者故事 | 驗收條件（Given–When–Then） |
| --- | --- | --- |
| US-VIS-01 | 作為訪客，我想瀏覽社團、公告與活動資訊，以判斷是否加入或報名。 | **Given** 未登入，**When** 開啟公開頁，**Then** 可閱讀公開內容且不會看到社員資源或名單。 |
| US-APP-01 | 作為訪客，我想提交入社申請，以便成為社員。 | **Given** 我填妥必填資料並同意個資告知事項，**When** 送出申請，**Then** 系統建立「申請中」紀錄並顯示申請已送出。 |
| US-APP-02 | 作為幹部，我想審核入社申請，以便決定申請人是否成為社員。 | **Given** 我有入社審核權限，**When** 核准、退回或列候補，**Then** 系統記錄決策者、時間、原因與新狀態，並通知申請人。 |

### 2.2 社員與活動

| ID | 使用者故事 | 驗收條件（Given–When–Then） |
| --- | --- | --- |
| US-MBR-01 | 作為社員，我想維護自己的基本資料與通知偏好，以確保活動通知可正確送達。 | **Given** 我已登入，**When** 更新本人資料，**Then** 僅本人資料被更新，且必要欄位會經格式驗證。 |

| US-EVT-02 | 作為社員，我想取消活動報名，以釋出名額。 | **Given** 我已有有效報名且尚未超過取消期限，**When** 取消報名，**Then** 系統更新名額與狀態並保留操作紀錄。 |
| US-EVT-03 | 作為幹部，我想建立活動及管理名單，以完成活動行政。 | **Given** 我有活動管理權限，**When** 建立或修改活動，**Then** 系統驗證日期、名額、公開範圍與報名規則，並於發布後依規則開放報名。 |

## 3. Draft 商業規則

以下是可供開發估工的預設規則。標記為「待確認」的內容不得在正式實作時自行假設，應列入需求工作坊決策。

| 編號 | 規則 | Draft 預設 | 狀態 |
| --- | --- | --- | --- |
| BR-01 | 入社申請資格 | 訪客可提出申請；一個 Email 在同一時間只能有一筆未結案申請。 | 待確認。 |
| BR-02 | 會員狀態 | `申請中 → 社員 → 停用／離社／校友`；只有有效社員可存取社員內容。 | 待確認。 |
| BR-03 | 專案生資格 | 專案生必須是有效社員，且可同時被指派到多個專案。 | 待確認。 |
| BR-04 | 幹部任期 | 幹部可具多個職務；每個職務必有開始日與結束日。 | 待確認。 |
| BR-05 | 活動資格 | 預設開放社員報名；活動可另設為公開、專案限定或幹部限定。 | 待確認。 |
| BR-06 | 候補排序 | 依報名完成時間遞補；自動遞補延至第二期，MVP 由幹部手動處理。 | 已建議。 |
| BR-07 | 取消期限 | 每場活動可設定取消期限；未設定時不允許系統自動假定。 | 待確認。 |
| BR-08 | 資源權限 | 資源可標示為公開、社員、專案、幹部；下載前於伺服端驗證。 | 已建議。 |
| BR-09 | 個資最小化 | MVP 僅蒐集流程所需資料；不將身分證、金融帳戶或未必要的敏感資料納入。 | 已建議。 |

## 4. 範圍外與第二期接點

第二期需求不刪除，而是保留資料與架構接點：任務可日後掛在 Project 下，QR 報到可掛在 EventRegistration 下，資源版本可掛在 Resource 下，交接包可掛在 Department／OfficerAssignment 下。這樣可以避免 MVP 因功能不足而重構核心資料表。

本節以社長回覆為準，若與前文的 Draft 預設不同，應以本節覆蓋。其中特別保留「校外申請者」與「學號／學校信箱驗證」之間尚未釐清的帳號啟用方式，待決策後才可鎖定認證流程。

| 決策項目 | 已確認規格 | 對 MVP 的影響 |
| --- | --- | --- |
| 產品決策者 | 社長擔任最終需求與流程決策者。 | 所有需求異動與 UAT 簽核由社長確認。 |
| 第一期間範圍 | 採用既定 MVP：公開資訊、申請／會員、活動、資源、專案基礎、幹部任期與 RWD。 | AF-04、AF-05、AF-07 至 AF-14 維持第二期或後續評估。 |
| 帳號識別與啟用 | 校內使用者以**學號**作為帳號識別；使用者先在學校信箱接收認證碼／驗證連結，驗證後才可自行設定或修改密碼。 | 需新增帳號啟用、驗證碼／連結有效期限與密碼設定畫面。 |
| 入社程序 | 入社包含申請表、書面審查與面試，不以表單送出即直接核准。 | 申請狀態、審查評語、面試排程與決策歷程納入 MVP。 |
| 招生對象 | 校內與校外人士皆可申請；兩者的招生說明與時程不同。 | 需新增招生梯次／類型與對應時程，公開頁可顯示不同資訊。 |
| 專案生 | 專案生必須是有效社員；專案生需參與專案實作，社員不一定需要。 | `ProjectAssignment` 成為專案生資格的唯一系統依據。 |
| 活動範圍 | 預設社員活動；個別活動可設為公開、專案限定或幹部限定。 | Event visibility 採四級範圍與後端資格檢核。 |
| 幹部任期 | 職務具開始日與結束日；到期前通知，到期自動移除管理權限。 | 需加入到期通知排程與自動撤權 job。 |
| 資源分級 | 公開／社員／專案／幹部四級。 | Resource visibility 與下載授權採四級判斷。 |
