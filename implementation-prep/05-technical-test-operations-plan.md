# 05｜技術啟動、測試與營運治理計畫

**狀態：** v1.0（MVP 開發準備定版；production 治理另有上線門檻）  
**目標：** 在功能實作前建立可重現的技術環境、最低安全基線、測試策略與上線／交接責任，避免社團因換屆或單一個人帳號而失去系統控制權。

## 1. 架構決策紀錄（ADR-001）

### 決策

第一期採用**Next.js＋TypeScript＋PostgreSQL 的模組化單體架構**，以單一程式庫承載公開前台、會員區、幹部後台與伺服端 API／BFF。Next.js 官方文件提供全端 React 應用、路由、資料取得、路由處理、表單、快取、部署與測試相關能力，適合第一期的功能密度與維運人力。[1]

### 理由與邊界

此方案可降低前後端分離的驗證、API 契約、部署與監控複雜度；資料庫採關聯式 PostgreSQL，以對應會員、角色、任期、活動、報名與專案的明確關係。若未來需要多校支援、公開 API、行動 App、複雜背景排程或高頻整合，再將後端模組拆分至 NestJS；NestJS 的 TypeScript 模組化架構可作為演進選項。[2]

| 層次 | 第一期間建議 | 必須先決定的事項 |
| --- | --- | --- |
| Web 應用 | Next.js App Router＋TypeScript。 | 代碼庫命名、擁有者、部署方式。 |
| UI 與表單 | Tailwind CSS＋可近用元件庫；React Hook Form＋Zod。 | 設計 token、表單錯誤文案與語言。 |
| 認證 | 校內採「學號＋學校信箱 Email 認證碼＋密碼」；校外採「已驗證外部 Email＋Email 認證碼＋密碼」。 | 寄件服務、認證碼有效期與重寄節流參數。 |
| 授權 | 伺服端 RBAC＋Membership／ProjectAssignment／OfficerAssignment 範圍判斷。 | 權限代碼、各部門資料範圍。 |
| 資料庫 | 受管 PostgreSQL＋Migration 工具（Prisma 或 Drizzle）。 | 正式資料擁有者、備份與保留期間。 |
| 檔案 | S3 相容物件儲存，以受簽名或權限化下載存取。 | 檔案上限、允許類型、公開／內部原則。 |
| 通知 | MVP 使用網站內通知＋交易 Email。 | 寄件人信箱、通知事件、發送責任人。 |
| 可觀測性 | 錯誤追蹤、結構化日誌、可用性監控。 | 錯誤告警接收人、資料保存期間。 |

## 2. 程式碼、帳號與環境治理

| 領域 | 開發前必須完成 | 責任人 | 最低驗收條件 |
| --- | --- | --- | --- |
| 程式碼庫 | 建立社團組織帳號下的 Git 儲存庫、README、Issue 模板、PR 模板與 CODEOWNERS。 | 社長（暫代網站負責人） | 程式碼不只存在於個人帳號；正式 production 前需補足復原存取權。 |

| 環境分離 | 建立 local、staging、production 三環境，且環境變數與資料庫完全分離。 | 開發負責人 | 測試資料不寫入 production；staging 可部署供 UAT。 |
| 祕密管理 | 認證碼寄件金鑰、資料庫連線、儲存金鑰存於環境祕密管理，不進 Git。 | 社長（暫代網站負責人） | 儲存庫掃描無明文祕密；可輪替金鑰。 |

## 3. 安全與個資最低基線

| 控制領域 | MVP 實作規格 | 驗收方式 |
| --- | --- | --- |
| 身分驗證 | 校內以學號識別、校外以已驗證 Email 識別；寄送一次性 Email 認證碼後才可設定或修改密碼；session 使用 HTTP-only Secure Cookie。 | 登入、登出、認證碼過期／錯誤／重寄、帳號停用與密碼重設測試。 |
| 授權 | 每個讀寫 API 依權限與資料範圍驗證；不僅依前端隱藏按鈕。 | 使用無權限帳號直接呼叫 URL／API，必須取得拒絕結果。 |
| 輸入與輸出 | 所有表單使用 schema 驗證；內容顯示進行輸出編碼；上傳檔案限制類型、大小與掃描策略。 | 惡意／過長／缺欄位資料與不允許檔案測試。 |
| 資料最小化 | 只收集入社、報名與通知所必需資料；不在 MVP 收集身分證、金融帳戶或不必要敏感資訊。 | 資料字典與表單逐欄核對。 |
| 稽核 | 會員審核、角色變更、資料匯出、公開發布、刪除等操作寫入 append-only AuditLog。 | 進行高風險操作後可查到操作者、時間與目標。 |
| 備份與復原 | 資料庫每日備份；檔案儲存有版本／生命週期；定義復原聯絡人。 | staging 完成至少一次測試還原演練。 |
| 管理帳號 | 社長暫代網站負責人；高風險操作需要再確認。D-15 的共用帳號與 MFA 在正式 production 前需採暫行資產持有與復原方案，並於下一次 MVP 完成正式治理。 | 上線前檢查暫行方案、操作確認與復原文件。 |

## 4. 測試策略與品質門檻

### 測試層級

| 測試層級 | 範圍 | 範例 | 負責時點 |
| --- | --- | --- | --- |
| 單元測試 | 純商業規則、欄位驗證、狀態轉換。 | 名額判斷、候補排序、任期有效性。 | 每個功能開發時。 |
| 整合測試 | API、資料庫與權限中介層。 | 未授權者不可讀取專案資源；核准申請會建立社員狀態。 | Pull Request 與 staging 前。 |
| 端對端測試 | 真實使用者流程與瀏覽器互動。 | 訪客申請入社、社員報名、幹部建活動、網站負責人換屆。 | 每次 MVP 發布前。 |
| RWD／可近用性測試 | 不同裝置寬度、鍵盤、焦點與表單。 | 320px 報名、iPad 資源篩選、鍵盤使用對話框。 | 每個主要 UI 完成後與 UAT 前。 |
| 安全與回歸測試 | 權限、輸入、session、檔案與資料匯出。 | 直接 URL／API 存取、受限下載、停用帳號。 | 上線前與高風險改動後。 |

### Definition of Done（單一功能完成定義）

| 條件 | 要求 |
| --- | --- |
| 需求 | 使用者故事、商業規則與驗收條件已連結至 Issue／Ticket。 |
| 設計 | 已有正常、空白、錯誤、載入與無權限狀態；RWD 行為已指定。 |
| 程式 | 通過 lint、型別檢查與必要測試；未新增明文祕密。 |
| 權限 | 讀寫操作均在伺服端驗證；稽核行為已補上。 |
| 測試 | 正向、錯誤與無權限情境通過；主要手機與桌機斷點已確認。 |
| 文件 | API、資料欄位、管理操作或使用說明已更新。 |
| 驗收 | 產品負責人或指定幹部在 staging 簽核，或明確將缺陷列入 backlog。 |

## 5. UAT 測試腳本

| UAT ID | 角色 | 任務 | 成功判定 |
| --- | --- | --- | --- |
| UAT-01 | 訪客 | 在手機選擇校內／校外招生梯次並提交書審申請。 | 不需協助即可完成；可清楚辨識不同說明與時程；送出後可查看關卡與後續指示。 |
| UAT-02 | 校內社員 | 以學號發送學校信箱認證碼、完成密碼設定、登入、報名活動並取消。 | 認證碼安全、正確、可理解；名額／候補與取消結果即時、正確。 |
| UAT-03 | 專案生 | 在手機查看所屬專案公告並下載資源。 | 只能看到所屬專案；下載與權限提示清楚。 |
| UAT-04 | 幹部 | 在桌機建立活動、發布、查看名單並登錄出席。 | 所有必填規則、狀態與名單資料正確。 |
| UAT-05 | 人才發展部長＋社長 | 登錄書審／面試結果，並由社長最終核准及啟用帳號。 | 審核者與核准者權限正確分離，歷程完整，核准者可收到認證碼啟用流程。 |
| UAT-06 | 社長（暫代網站負責人） | 指派下一任幹部、設定任期結束並查閱稽核紀錄。 | 新任權限生效、舊任權限依規則失效，稽核完整。 |

## 8. 已確認決策增補：認證、招生與治理例外

### 8.1 校內帳號啟用與密碼設定

校內使用者以學號作為帳號識別，並需先以學校信箱完成一次性認證，才允許設定或修改密碼。此流程應實作為受時間限制、可撤銷、不可重複使用的啟用程序；系統僅儲存密碼雜湊與驗證憑證的雜湊，不保留明文密碼、明文認證碼或可重複使用的驗證連結。

| 步驟 | 系統行為 | 安全控制 |
| --- | --- | --- |
| 1 | 使用者輸入學號並請求啟用／重設密碼。 | 僅對已核准且具學校信箱資料的校內使用者提供流程；回應訊息不得洩漏帳號是否存在。 |
| 2 | 系統寄送一次性 Email 認證碼至已登錄的學校信箱。 | 認證碼設有效期限、使用次數限制與重寄節流；資料庫只存雜湊。 |
| 3 | 使用者輸入 Email 認證碼完成驗證。 | 完成後立即失效；逾時或已使用的認證碼不可再啟用。 |
| 4 | 系統開放使用者設定或修改密碼。 | 密碼只以強雜湊保存；設定成功後建立新的安全 session 並寫入稽核。 |

> **定版規則：** MVP 採「輸入 Email 認證碼」作為唯一啟用／重設驗證方式；不再要求驗證連結。

### 8.2 校內外招生與入社審核

| 項目 | 已確認規格 | 技術影響 |
| --- | --- | --- |
| 招生梯次 | 校內與校外各自有說明與時程。 | 需建立 `RecruitmentCycle` 並由 CMS／後台設定梯次內容與時間。 |

| 校外登入 | 校外通過者以已驗證的外部 Email 作帳號識別並使用 Email 認證碼啟用。 | 外部 Email 驗證與密碼設定流程納入 MVP。 |

### 8.3 幹部任期與權限回收

| 需求 | 已確認規格 | 技術實作 |
| --- | --- | --- |
| 到期提醒 | 任期結束前通知。 | 排程每日檢查有效 OfficerAssignment，於可設定的提前天數發送一次提醒並記錄。 |
| 自動撤權 | 到達結束日自動移除管理權限。 | 權限查詢必須即時計算有效日期；另以排程將 assignment 標示為 ENDED 並寫入 AuditLog。 |

### 8.4 D-15 延後至下一次 MVP 的影響

社長決定將「社團共用信箱、雲端服務共同持有與 MFA」延後至下一次 MVP。此決策可讓目前先完成需求與原型，但會使正式部署、帳單續費、帳號復原與換屆交接缺乏足夠治理。因此，將其記為**延後功能**，但不是可忽略的上線風險。

| 目前可進行 | 在 D-15 未完成前不可視為完成 |
| --- | --- |
| 建立需求文件、wireframe、資料模型、程式原型與 staging 測試。 | 在沒有資產持有人與復原文件時使用任何帳號進行正式 production 部署。 |
| 撰寫權限、備份、交接與 MFA 實作規格。 | 正式公開上線後，卻沒有可復原的服務帳號、備援人或帳務責任人。 |

> **上線關卡：** D-15 可以不列入目前的 MVP 功能開發，但在第一次正式 production 上線前，社長必須以暫代網站負責人身分簽核具期限的資產持有與復原方案；共用信箱、共同持有與 MFA 則在下一次 MVP 完成正式化。
